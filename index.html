One front door. A visible chain.

Orders go down. Evidence comes up. Choose a node or a gate to see where the work goes, and where it has to stop.

the Axiom systema map, not a live activity feed

OWNER → OPERATOR → WORKERS: orders down, evidence up. axioma and gatekeeper sit before WORLD; standing checks returning evidence. tripwire records a refused action in REFUSAL LOG. handydandy prepares the handoff to NEXT SESSION.

Follow the chain.

The owner sets the limits. The operator routes work to specialists, and evidence returns along the same chain.

Hover, tap or use the keyboard. Escape clears the selection.

Owner / the authority

The owner sets the limits and decides what may commit the business. A draft is never that approval.

Operator / one front door

The operator routes work to specialist workers and brings their evidence back to the owner.

Workers / bounded work

Specialists do the assigned work and return evidence up the chain. Saying “done” is not a check.

Next session / continuity

A written handoff carries the work forward so the next session can pick up where this one stopped.

World / outside the session

A message to another person leaves the session. The outbound edge is where the advisory card and send checks sit.

Refusal log / a visible stop

A refused action leaves a record instead of disappearing. Tripwire watches tool refusals, not just outbound sends.

axioma / a second look

Before a consequential call, Axiōma presents an advisory card. It advises; it never blocks or grants permission.

The spec is CC0 and the code is MIT.

gatekeeper / before a send

Checks supported terminal sends for consent, suppression, quiet hours and repeat messages. A failed check blocks that send.

standing / check the evidence

A worker must run a passing proof check before marking its task done. Standing checks the file, page or allowed command, not the claim.

tripwire / record a refusal

Logs a refused tool action and alerts the owner. It records the stop; it does not grant an exception.

handydandy / leave a handoff

Notices when a session runs long and prompts a written handoff for the next session.

The chain and its limits: hermes-axiom-agent, public source. The plugins act at different points; an advisory card is not an approval.

Where an agent stops and asks

drag the medallion · the words make room · arrow keys work too

the marked phrases are lit; the key below explains each color

Around 520 BC, Hipparchus of Athens set stone herms along the roads and carved short maxims into them, so anyone walking past could read the law on the messenger's stone. Walk with just intent. Do not deceive a friend.

We run our own company on the same idea. About a dozen (second look) specialist AI agents work behind one front door, and a written permission gate decides what each one may do alone. Money, new prices and first contact with strangers wait for a person.

An agent can build a payment link and check that the page opens. It never presses pay: completing a live payment (STOP) is reserved to the owner, so the agent stops there and reports exactly what is ready.

Every message is reserved before it sends, because a worker that crashes and retries could text the same person twice (CAUTION). We would rather miss one message and see it in the log than send it twice. The loop that answers when an agent gets stuck is public code, with 9 passing tests (GO).

Those colors are Axiōma, the signal our agents use when they write to a person. Red is stop, yellow is caution, green is a check that really passed, and pale gold is a whisper. The signal advises. The gate stays with you. Axiōma is given away: the spec is CC0 and the code is MIT.

# each marked phrase carries its Axiōma signal color and a second cue besides color:

  • red, bold, solid line: stop. Do not proceed until it is fixed.
  • yellow, wavy line: caution. It works, but it starts something that cuts against your interest.
  • green, dashed line: go. A real check passed.
  • pale gold, dotted line: whisper. A second look; it stops nothing.

Method

When rules and regulations begin to move, it's no longer solely governance. It's operations.

Before a system runs, we write down what starts the work, what counts as done, and where it has to stop and ask.

  1. 01Intake.A request, message or deadline enters the system.
  2. 02Context.Prior notes and decisions are gathered first, so the owner is not asked to explain again.
  3. 03Preparation.The draft, the edit or the next action is produced in full.
  4. 04Decision.Anything that commits the business waits for the owner.
  5. 05Record.The outcome is checked and written down, so the next session starts where this one ended.
